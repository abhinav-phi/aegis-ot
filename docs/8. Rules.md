# AEGIS-OT — Development Rules

> **Version:** 1.0
> **Last Updated:** 20 August 2026
> **Purpose:** Mandatory rules for all engineering and research on AEGIS-OT. Follow strictly. Violations are documented in the audit log / code review.

---

## 1. Security Rules (NON-NEGOTIABLE)

### R1 — Never connect autonomous response to real SCADA infrastructure
- ❌ Never execute a generated command on any real PLC/RTU/HMI/plant device — in a lab or otherwise.
- ✅ All generated actions are **sandbox-only**; the pipeline's terminal stage is `pipeline/sandbox`.
- ✅ Networking isolation: the sandbox has **no route** to any OT device; only loopback + internal service.

### R2 — Never execute generated commands directly
- ❌ The agent's `propose_action` may never be a raw command string interpreted by the OS.
- ✅ Actions are structured `{action, target, params}` objects validated against `configs/policy/*.yaml` grammar before any use.

### R3 — Human approval required for control-class actions
- ❌ A `control`-class step may never reach the simulator without an `approved` approval_requests row.
- ✅ Approval row created by the approval service only (SAFE-03); decision recorded with actor + reason (deny requires reason).
- ✅ Approvals auto-expire after 24 h → plan/incident **escalated** to admin review (never silent deny, never silent execution) (AppFlow §5/§6).

### R4 — Sandbox-only execution
- ✅ The ONLY executor in the codebase is `pipeline/sandbox/simulator.py`.
- ✅ Simulator output is always labeled `SIMULATED` in DB (`simulated_actions.status`) and UI.

### R5 — Least privilege
- ✅ Agent tools receive **read-mostly** surfaces: `query_latest`, `query_history`, `search_kb`, `check_invariant`, `propose_action`. No shell, no DB write, no file write beyond sandbox.
- ✅ Service accounts: pipeline worker ≠ API user ≠ eval runner. Each has only what it needs.

### R6 — Secrets management
- ❌ No secrets in frontend bundle (`.env*` local only; env split per R6).
- ✅ `AEGIS_OT_SECRET_KEY`, `DATABASE_URL`, MinIO/Chroma/Ollama creds **server-side** config only, validated by Pydantic Settings at boot.
- ✅ `.env` gitignored; `.env.example` committed.

### R7 — Input validation
- ✅ Server-side validation is mandatory (Pydantic schemas + DB CHECK constraints).
- ❌ Never trust client/user input alone — every mutation re-validated at the API boundary and in the validator.

### R8 — Prompt-injection defenses (the research core)
- ✅ Treat **all telemetry/log/document content as adversarial input** (2026 log-substrate injection literature: LogJack, LogInject, Poisoning-the-Watchtower).
- ✅ Provenance-aware rendering: tier-tagged chunks; hostile tier never silently merged into instructions.
- ✅ Validator runs C1–C5 on every plan (R9 below); result always stored.

### R9 — Validator ordering (fail-fast, recorded)
- ✅ C1 provenance → C2 allowlist → C3 pattern filter → C4 risk class → C5 consistency.
- ✅ Each check writes result to `validator_results.checks`; verdict is a soft-min (block/require_approval/allow/escalate).
- ✅ Determinism (AEGIS-04): C1–C4 are deterministic code; C5 is deterministic-where-possible (rule-based entailment/field match) — no validator check runs the planner's own model; every check records its `deterministic` flag.
- ❌ Never skip a check "because the prompt looks safe".

### R10 — Untrusted telemetry treated as untrusted
- ✅ Sensor values with provenance flags (e.g., WUSTL-IIoT label columns) carry source metadata; explanation may cite but never *silently comply* with instructions embedded in them.

### R11 — RAG source validation
- ✅ KB documents versioned (`rag_documents.doc_hash`, `version`); every chunk cites `document_id`.
- ✅ Hostile fixtures live **only** in the evaluation KB collection — production KB never poisoned (RAG-06).

### R12 — Evidence citation
- ✅ Any factual claim in an explanation or mitigation must carry a chunk/tool citation.
- ✅ Answer with "insufficient data" when no evidence supports the claim (alone is allowed).

### R13 — Audit every agent action
- ✅ Every tool call, draft, verdict, approval, and simulator action writes to `audit_logs` (append-only, no UPDATE/DELETE policies).
- ✅ Every mutating API handler writes audit rows before returning.

## 2. AI / ML Rules

### R14 — Roles are server-authoritative
- ✅ `user_roles` changeable only via `app.core.security.set_role()` (admin) — no client-side role writes, no defaults that escalate.

### R15 — Never fabricate detection results
- ✅ Detections come from the detector pipeline and are written with the exact model_version + threshold used.
- ❌ No hand-edited "better" numbers in demos or slides. Demo numbers are regeneration from committed configs.

### R16 — Never fabricate threat intelligence
- ❌ Do not invent technique IDs or threat intel in explanations. Every `threat_mappings` row cites its basis (rule + citations).

### R17 — Raw data storage
- ✅ Raw telemetry and feature blocks go to MinIO; PostgreSQL stores references + metadata only (`datasets`, `dataset_runs`).

### R18 — Never treat attention as explanation
- ✅ Attention weights may be recorded (diagnostics) but are NEVER presented as explanations (XAI-04). Use reconstruction-error attribution for explainability.

### R19 — Never claim LLM diagnosis is ground truth
- ✅ All agent output is decision support; `closed_reason` and UI labels say "diagnosis is hypothesis".
- ✅ The explanation pathway (XAI-01/-02) is a hypothesis/summary path with no execution authority: it consumes only structured attribution + invariant evidence (prompt forbids citing anything else) and is NOT equivalent to the C1–C5 mitigation validator (R12 evidence rule still applies).

### R20 — Model versioning
- ✅ Every detector training run inserts a `model_versions` row + MLflow run; inference binds to model_version_id (no silent retrains).

### R21 — Track datasets
- ✅ Every eval uses pinned dataset sha256 (registry); no unrecorded dataset swaps.

### R22 — Reproducible experiments
- ✅ Every experiment = config file with hash; reruns must start from same hash (EVAL-07). Seeds pinned and recorded.

### R23 — Prevent train/test temporal contamination
- ✅ Temporal splits only; normalization + threshold from train/validation; tests separate (leakage test in CI).

## 3. Research Rules

### R24 — No unsupported novelty claims
- ❌ No "first ever", "SOTA", "state-of-the-art", "#1" — without a citation to the specific claim being beaten.
- ✅ Use narrow comparisons: "SWaT detector F1 vs. published leaderboard (TFMAE 98.36, ICDE'24)" or "injection suite not covered by InjecAgent (ACL Findings 2024 — email, finance, smart-home) or AgentDojo (NeurIPS D&B 2024 — banking, Slack, travel, workspace)" (domains as in PRD §1.1).

### R25 — Distinguish hypothesis from result
- ✅ PRD Success Criteria are labeled as hypotheses/targets; measured values only in `metrics` tables and the eval report (Rules R15).

### R26 — Report negative results
- ✅ If the proposed detector does not beat baseline F1, say so; robustness/stress is the defensible claim.

### R27 — Report the full metric set (no cherry-picking)
- ✅ Report FPR, PR-AUC, detection latency, inference latency — not just F1.
- ✅ Report hallucination rate, citation correctness, RAG grounding — not just "it looks right".

### R28 — Ablation studies
- ✅ EXP-03/-04:-07 run as fixed variants; ablation rows report the same metrics as the full system.

### R29 — Baseline comparisons
- ✅ Always compare proposed vs the MVP baseline (Isolation Forest) on the same splits; LSTM-AE applies only if the stretch ablation (DET-06) is built.

### R30 — No model stacking
- ❌ Do not bolt on ANFIS/fuzzy/Transformer "because soft computing" — add only if a documented experiment shows gain or robustness value (TechSpec §3.2).

## 4. Development Rules

### R31 — Type safety
- ✅ Python: type hints on all public functions; mypy strict on `pipeline/`, `app/`.
- ✅ TS strict mode; typed API client (`lib/api.ts`).

### R32 — Error handling
- ✅ Every async API route: catch → structured error → toast/log; no swallowed exceptions.
- ✅ Every pipeline stage has a failure path recorded to `audit_logs` (entity_type=`pipeline`).

### R33 — Logging
- ✅ JSON structured logs w/ request_id; no bare `print()` in service code (dev-only `logger.debug` allowed).

### R34 — Testing
- ✅ `make test` green before merge: pipeline units, validator fixtures (30 actions), approval round-trip integration, leakage test, eval determinism (seeded).

### R35 — Configuration
- ✅ All tunable knobs in `configs/*.yaml`; no hardcoded thresholds in source.

### R36 — Docker / reproducibility
- ✅ `docker compose up` runs the stack; `Makefile` targets script the rest; fresh-checkout command in README.

### R37 — Git conventions
- ✅ One feature per commit; prefix `feat:`, `fix:`, `test:`, `docs:`, `chore:`; never `updates`/`fix stuff`.
- ✅ Build/tests pass before push.

### R38 — Documentation requirements
- ✅ Every module `docstring` explains role; README documents run commands; Tracker.md updated within 24 h of milestones.

## 5. Demo Rules

### R39 — Clearly label simulated data
- ✅ Every demo screen shows dataset + `SIMULATED`/`FIXTURE` badges; attack fixtures watermarked in the stepper.

### R40 — Clearly label simulated actions
- ✅ `simulated_actions` rows and UI: "Simulated execution — no real plant was touched."

### R41 — Never present mock results as real
- ✅ Demo numbers regenerate from committed config; if a number is a target it says "TARGET" not "RESULT".

### R42 — Never present expected metrics as achieved
- ❌ No "we achieved 98% F1" in slides unless measured and in `metrics` table.
- ✅ Presentation states hypotheses separately from measured outcomes (Rules.md R25).

| INV-011 | Validator failures fail closed | check exception ⇒ require_approval floor; 2nd ⇒ escalate |
| INV-012 | Hostile eval-KB content never becomes trusted production evidence | collection separation + retriever allowlist |
| INV-013 | Audit rows accompany security mutations in the same transaction | audit service + same-tx writes |
| INV-014 | Every executed action is simulated and labeled | single executor + SIMULATED labels |
| INV-015 | ≤1 active agent run per incident | partial UNIQUE index |
| INV-016 | Datasets/artifacts verified before use | verify-at-load sha256 |

### New rules

### R43 — Amendment re-validation
Any amendment creates a NEW immutable plan revision and runs fresh C1–C5
before any approval of that revision. The prior approval is superseded in the
same transaction. There is no amend→execute path without fresh validation.

### R44 — Naive isolation
gent_runs.variant='naive' ⇒ no approval creation, no amendment, no sandbox
execution, plan status locked to draft_only. Enforced at service layer AND
sandbox AND evaluation harness.

### R45 — Content binding
Execution without a matching triple hash (plan ↔ active validator result ↔
approved approval) is forbidden and audited (EXEC_HASH_MISMATCH).

### R46 — Fail-closed defaults
Guard, scheduler, and validator failures RESTRICT capability; they never relax
a safety state.
