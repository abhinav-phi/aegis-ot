## 3. ML Pipeline (Detection → Explanation)

### 3.1 Pipeline Stages

```
SCADA/OT data (Parquet in MinIO)
  → [preprocess] gap/NaN handling, z-score normalization (fit on TRAIN ONLY)
  → [features] rolling window W=60 (1s samples), stride S=1
  → [detect]
       training: fit TCN-AE on normal-only windows (LSTM-AE only as a stretch ablation, DET-06)
       inference: reconstruction residual per sensor e_t
       score: normalized reconstruction error per window
       classify: confirmed-anomaly windows via validation threshold
  → [attribution] per-sensor error decomposition (top-contributing channels)
  → [explain] structured Explanation object + NL summary (agent writes it)
  → [invariants] physics-bound checks (SWaT stage constraints from literature)
  → [incident] grouped anomaly windows → incident object with severity
```

**Explanation-path safety boundary (known limitation):** the NL explanation
(`[explain]` above) is produced from structured attribution + invariant
evidence only (prompt forbids citing anything else). It is a human-readable
hypothesis (R19), NOT an execution authority and NOT equivalent to the C1–C5
mitigation validator (SAFE-01/-03): unsupported instructions hidden in raw
telemetry/log text are never promoted to instructions through this path (R12).

### 3.2 Model Selection (compare, don't stack)

| Model | Type | Role | Status |
|---|---|---|---|
| **Isolation Forest** | density/iforest on window features | **Baseline** — strong, cheap sanity check | Core |
| **TCN-AE** (proposed) | reconstruction, dilated causal convs | **Proposed detector**; dilated causal convs give long receptive field cheaply and stable gradients vs LSTM | Core |
| **LSTM-AE** | reconstruction, recurrent | Stretch ablation (DET-06) — retired from core baselines | Stretch (DET-06) |
| XGBoost | gradient boosting on aggregate features | Ablation only (DET-07) — not a baseline | Stretch (DET-07) |
| **Transformer-AE** | reconstruction, attention | Ablation only — higher variance, needs more tuning/data | Stretch (DET-07) |
| ANFIS / neuro-fuzzy | fuzzy rules | Windowed channel-importance robustness study only (syllabus-aligned, not core) | Stretch (DET-07) |

**Why TCN-AE and not a vanilla Transformer as primary:** On sub-minute window sizes with ~1M samples, a Transformer's data-hunger and attention-based attribution ambiguity do not justify a primary role for the capstone scope. *Attribute via reconstruction-error decomposition* (simple, inspectable, monotone in per-channel residual), rather than attention weights — see Rules.md R18 (never treat attention as explanation).

**Data leakage avoidance (hard rules):**
- Normalization and threshold selection happen **on the training partition only**.
- Splits are **temporal**: train = first N days of SWaT normal runs, validation = holdout normal + attack days, test = held-out attack runs. **No random shuffle across time.**
- Stress protocol augments the **test** distribution only (no test-time calibration).

### 3.3 Anomaly Scoring

```
residual_t = || x_t - x̂_t ||_2  (per sensor)
window_score = mean over sensors of normalized residual
threshold τ  = quantile on validation GT-normal residuals only (p99 default)
anomaly = window_score > τ
sensor_contribution_i = residual_i / Σ residual_j   (top-k shown)
```

### 3.4 Invariants

- Literature-known SWaT physical constraints (e.g., tank level stays within sensor ranges; pump status correlated with flow) encoded as cheap boolean checks merged into the Explanation object as corroborating/contradicting evidence.
- `check_invariant` is also an **agent tool** so the agent can ask for invariant states before proposing an action.

## 4. RAG Subsystem

### 4.1 Knowledge Base (KB)

| Corpus | Source tier | Trust | Used for |
|---|---|---|---|
| MITRE ATT&CK for ICS techniques + descriptions | trusted | `trusted` | Threat mapping (RAG retrieval + static mapping table) |
| SWaT plant documentation / papers (sensor semantics) | trusted | `trusted` | Sensor/plant context |
| Response playbooks (team-written, standard IR steps) | trusted | `trusted` | Mitigation drafts |
| Threat reports / CTF writeups (public) | public | `public` | Attack-the-agent poisoning surface |
| Injected "manual pages" (demo fixtures) | adversarial | `hostile` | Attack-the-agent demo (F2/F4) |

### 4.2 Pipeline

```
documents → chunker (heading-aware, ~200–400 tokens, overlap 32)
  → embedder (sentence-transformers all-MiniLM-L6-v2 or bge-small)
  → Chroma collection (per run; metadata: doc_id, source_tier, section)
  → retriever (top-k=5, metadata filter for tier)
  → citations: [ {chunk_id, source, section, tier} ]
```

### 4.3 Provenance & Trust Tiers

- Every chunk carries `tier ∈ {trusted, public, hostile}`.
- **Retrieval output tells the builder and the agent the tier** — hostile/public content is surfaced as "untrusted evidence: verify manually", never merged silently into instructions.
- Injection-suite fixtures write `hostile` documents into a **separate evaluation KB collection** — production KB is never polluted (Rules.md R11).

## 5. Agent & Validator Architecture

### 5.1 Single Planner Agent (deliberate)

**Why a single agent (not a swarm):** the RQ3 measurement ("does gating reduce unsafe actions") is confounded the moment we add second/third agent autonomy. One ReAct agent + an **external policy gate** isolates the variable we're measuring. (Differentiation from Competitor 5's multi-agent MARL design.)

```
agent_runs.agent_run
  │  state: { incident, evidence[], tool_call_log[], drafts[], verdict }
  ▼
LLM loop (LangGraph ReAct node)
  ├─ tools:
  │    query_latest(stream, sensors)      → telemetry.Window
  │    query_history(incident_id, span)   → telemetry.Window[]
  │    search_kb(query, tier_filter)      → RAG citations
  │    check_invariant(rule_id)            → bool/float
  │    propose_action(action, target, params) → DRAFT (pre-validator)
  ├─ system prompt: ground every claim in tool output; cite chunk ids;
  │     refuse unverifiable claims → "insufficient data"
  └─ end: mitigation_plans.mitigation_plan (steps[])
```

### 5.2 Validator + Policy Engine

Ordered checks (fail-fast; each recorded in `validator_results`):

> **Determinism** (AEGIS-04): C1–C4 are **deterministic code** — no LLM anywhere in the path. C5 is **as deterministic as possible**: rule-based entailment / field-match on rates and parameters; if an LLM-assisted check is ever added it must use a **different model than the planner** and be validated against the injection corpus. Every check records a `deterministic` flag (Schema §4.17).

1. **Provenance check** — are claims attributable to trusted tool/RAG output? Hostile tier cited → flag.
2. **Tool-arg allowlist** — action/target→allowed parameter grammar; path/stream names validated against schema.
3. **Suspicious-pattern filter** — known injection markers, command keywords on `write`/`control` paths, encoded payload patterns (base64, `!cmd`, `<sys>`)
4. **Policy classification** — action → risk class:
   - `read` → auto-allow
   - `write` (config/tuning) → require human approval
   - `control` (pump/valve/load changes) → require human approval **and** sandbox-only
   - `forbidden` (e.g., direct PLC write, crossing zone) → **block** (never silently executed; the separate `escalate` path is driven only by persistent C5 inconsistency, per R3)
5. **Consistency** — proposed steps vs. agent's cited evidence (cheap entailment / field match on rates) → mismatch flagged.

Output: `verdict ∈ {allow, require_approval, block, escalate}`, plus fine-grained `checks[]` with per-check pass/fail/flag.

### 5.3 Approval Gate + Sandbox Simulator

- `approval_requests` row created for every `require_approval` step (`status: pending`).
- Human confirms/denies/amends; only then does the simulator accept an action.
- Simulator: lightweight 6-stage SWaT-style proxy plant (tank levels, pump/valve state, flows) that applies actions and reports resulting telemetry shape; clearly labeled **SIMULATED**.

### 5.4 Attack Surface Addressed (evidence)

- **Log-substrate indirect injection** — 2025–26 preprints on IT/cloud/network domains (cited as motivating **analogy**, not OT evidence): LogJack (arXiv:2604.15368 — 0–86% verbatim exec across 8 models; RCE 6/8; cloud guardrails fail on log-formatted payloads), LogInject (arXiv:2607.14493 — up to 88.2% ASR on SOC log analysis; layered defenses cut 90.4% but leave 8.4% residual), Poisoning-the-Watchtower (arXiv:2605.24421 — summarization 96% injection success naive; persona S2 + structural S3 are the practical surface; direct override S1 now ineffective), NetInjectBench (arXiv:2607.10490 — metadata-aware policy gate: 0/240 unsafe actions under the integrity assumption; static allowlisting overblocks approved changes). **AEGIS-OT mirrors NetInjectBench's proven pattern**: execution-time policy gate (validator) + provenance-aware rendering + human review — but on OT domain data, which none of InjecAgent (ACL Findings 2024: email/finance/smart-home), AgentDojo (NeurIPS D&B 2024: banking/Slack/travel/workspace), or NetInjectBench cover.
